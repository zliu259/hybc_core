# 库房重做设计：项目配套清单、设备按台流转、物资流水、设备资料库

- 日期：2026-11-11
- 状态：第 2 版，待 owner 审阅第 17 节的决定。阶段 0、阶段 1 已上线（2026-11-11，迁移 0095，PR #24）；阶段 2 已上线（2026-11-11，迁移 0096，PR #25）；阶段 3 的接口和 Web 已上线（2026-11-12，PR #28，没有迁移；小程序没上传，通知开关没开）；阶段 4 拆成 4A 和 4B，4A（系统内的设备资料库）已实现（2026-11-12，本地验证通过，未上线，迁移 0097 没跑）。实施记录见第 21 节
- 依据：同日对库房/资产模块的全面审计、企微微盘 API 调研，以及在 owner 微盘里看到的现有资料
- 第 2 版相对第 1 版的变化：加入"项目配套清单"并把它作为发货和返库的主线；设备单和耗材单合并为一种库房单；物资分周转和消耗两类；资料库按现有资料的实际形态调整

## 1. 为什么重做

现有库房模块（2026-05 的任务队列重构）不能直接上线。审计确认的主要事实：

- Web 没有可达页面能新建仓库、物资类型、设备。
- Web 和小程序的出入库单只带"类型 + 数量"，从不带具体设备；后端只有带具体设备才移动设备、才生成返库检查任务。整套"返库检查 → 维护"模式从界面触发不了。
- 出入库执行不是原子操作、可重复执行；没有库存流水表；仓库里没有记录时出库也会成功。
- 盘点完成只改状态，不调库存。
- 库房任务没有任何企微通知；二维码生成是假按钮；4 个 AI 入口没有执行端。
- 操作手册库是原始 JSON 文本框，不能放文件，内容在 Web 和小程序都读不到。
- 小程序库房页有多处确定缺陷（首行无法编辑、成功后页面卡死、附件打不开、状态显示错误）。

逐条修补约 70 处问题，修完仍是一个概念过多的系统。库房表里没有生产数据，所以改为按更简单、更贴近实际做法的模型重做。

## 2. 现状：库房现在实际怎么做

2026-11-11 owner 扫码登录后，只读浏览了微盘公司空间。看到的事实：

### 2.1 出入库单其实是按工程的整套配套清单

- 文件夹"泥水土压设备材料计划表"由李震维护，每个工程一份表，标题是"土压设备出入库登记表"或"泥水设备出入库登记表"。
- 按机型（土压、泥水）各有一套约 195 行的模板，新工程直接复制上一个工程的表再改数量。
- 表头：编号、名称、规格、单位、计划数量、领取数量、使用丢失损坏数量、单价、总额、出库日期、退库日期、使用时间、备注。
- 表尾有三个签字栏：现场负责人、领料人、供应人（李震）。
- 11 个分节：顶进设备、辅助设备、注浆设备、控制照明系统、测量工具、工具、手动工具、劳动保护、施工消耗材料、生活设施、设备维修配件。
- 4 份表共 727 行，除计划数量外只填过一格（张家口那份的管钳，丢失损坏 6 把）。领取数量、单价、总额、出库和退库日期全是空的。
- 同一套模板，品名基本不变，规格随管径变。两份泥水清单（临河 DN1200、安定 DN600）约 180 行里有 126 行的规格或数量不同，例如排泥钢管一个是 Φ114、一个是 Φ80。
- 计划数量有 6 处不是数字（"25米""280米""若干"等）。备注里还会写上次的问题（"上次没来""上次是坏的"）。
- 备注里常写来源：现场买、现场采购、本地租、工地有、北京来料。
- 一个工程可以有多套设备：有的把数量翻倍写在一张表里，有的另起一张"第二套设备"。
- 同一张表里混着三类东西：
  - 按台的主设备：机头、油泵站、发电机、泥浆泵、注浆泵、电焊机、测量仪器。
  - 发出去要退回的周转件：顶镐、导轨、电缆、吊装链、扳手、集装箱。
  - 用掉的耗材：膨润土、电焊条、胶布、劳保用品。

结论：表格想管"计划、实领、丢失损坏、退库"，但靠表格管不动。系统要把这张表做成能自动填的。

### 2.2 顶管机约 30 台，每台一个资料文件夹

- 文件夹"顶管机参数、合格证、检测报告"下每台机器一个子文件夹，命名是"厂家-型号 + 机型"，例如"唐兴-NSPD1200泥水平衡""江都伟诚-NPD800泥水平衡顶管机""宏宇1050岩石破碎顶管机"。
- 机型有泥水平衡、土压平衡、岩石破碎、卵石破碎；口径 600 到 3500。同口径多台用后缀区分（DN1550-1、DN1550-2）。
- 每个文件夹里是合格证检测报告和技术参数的 PDF，50KB 到 9MB。
- 另有"设备说明书"（PDF 最大 36MB，以及图片）、"设备合格证"（图片和 PDF）、"测量仪器合格证"等文件夹。没有看到视频。
- 很多文件设了"外部可下载"，说明合格证和检测报告要发给外部单位。
- 上传人有多位（刘鹏最多，还有肖连忠、李震、刘昆、刘绍海等），不只是库管。

### 2.3 顶管机维修使用记录

## 4. 目标、不做的事、不能出现的事

### 目标

1. 现有那张配套清单的每一栏都由系统自动填：计划多少、实发多少、退回多少、丢失损坏多少、哪天出库哪天退库。
2. 每台设备在哪、能不能用，系统里随时是准的，并且不能靠手改。
3. 物资库存数字可信，每一次增减都有流水可查。
4. 李震用手机就能完成日常动作：按清单发货、返库清点、入库、派活、确认。
5. 干活的人打开任务就知道是哪台设备、要做什么、参考哪份资料。
6. 设备资料在 Web、小程序、微盘三处都能看，只需上传一次。
7. 该知道的人会收到企微消息，不再靠群里喊。

### 首期不做

- 多库房、库间调拨。
- 出入库和任务走审批引擎。
- 任务包、任务步骤、特殊放行。
- 顶管机组合方案、兼容规则、租赁周期。
- 库房相关的全部 AI 入口。
- 微盘往系统方向的同步。
- 采购流程和成本核算。单价只用来估算丢失损坏的金额。

### 不能出现的事

- 同一件事要李震录两遍。
- 任何能绕过检查的手改状态入口。
- 操作失败了界面没有提示。
- 微盘故障或限额导致系统里看不了资料。

### 操作步数目标

| 动作 | 目标 |
|---|---|
| 给新工程出配套清单 | 选模板，选项目，改数量，提交 |
| 按清单发货 | 打开清单，设备逐台扫码，物资确认数量，提交 |
| 一台设备返库 | 扫码，点"返库"，确认。3 步 |
| 工程结束清点 | 打开项目在场清单，填退回数和报损数，提交 |
| 做一个检查任务 | 打开任务，拍照，选合格或不合格，提交 |
| 找一台机器的资料 | 扫码，点"资料" |

## 5. 约束

- 技术栈不变：Hono + D1 + R2 + Queue（`packages/api`），Vue 3 + Element Plus（`packages/web`），原生企微小程序（`packages/miniapp`），bridge 固定 IP 虚拟机（`bridge/`）。
- 生产 D1 不支持 `BEGIN`，唯一原子的写法是 `db.batch()`。仓库里已有 `runAtomicBatch`（`packages/api/src/services/db-transaction.ts`）。带条件的 `UPDATE` 匹配 0 行不算错误，不会回滚。
- 企微接口要求可信 IP，所有企微 API 调用经 bridge。
- 小程序主包接近 2MB 上限，tabBar 页必须在主包。
- Worker 单次请求体上限 100MB，内存 128MB；现有上传是整文件读进内存后 `PUT`，不适合大文件。
- 推送到 `main` 即部署；D1 迁移是手动步骤。
- 约定：只做软删除，时间用 ISO 8601 文本，身份用企微 userid，流水号 `{前缀}-{年月日}-{序号}`，不用 `as any`。

## 6. 模型总览

- **设备**：一机一码，位置只有三种（在库、在项目、已报废）。
- **物资**：按数量管，分周转和消耗两类。周转件发到项目后记在项目名下，要退回或报损才算结清。
- **库房单**：所有改变设备位置或物资数量的动作都是一张库房单，一张单可以同时有设备和物资。
- **项目配套清单**：工程要什么的计划。发货和返库对着它做，实发、退回、报损自动回填。
- **任务**：检查、维修、保养、其他。只有一条状态线。
- **资料**：文件挂在设备或设备类别上，系统为主，微盘为镜像。

按台还是按数量，由库管在建档时决定。建议：有合格证或需要单独保养的按台管，其余按数量管。

### 6.1 表

新表全部新名字，与旧表不冲突。字段只列业务相关的，`created_at`、`updated_at` 按约定都带。

**人员与分类**

- `warehouse_member`：`userid`、`role`（`keeper` 库管、`doc_admin` 资料管理员），两者联合主键。初始库管一行（李震）。
- `device_category`：`id`、`name`（唯一）、`sort_order`、`status`。例如顶管机、油泵站、发电机、泥浆泵、测量仪器。
- 其余设置项（默认检查人、返库检查要求的照片数、微盘空间 ID 和镜像开关）存现有的 `system_config` 表。

**设备**

- `device`
  - `device_code`（唯一，默认生成 `SB-0001`，导入时可用已有编号）
  - `name`（例如"唐兴-NSPD1200泥水平衡顶管机"）、`alias`（现场叫法，例如"DN1550-1"）
  - `category_id`、`machine_type`（泥水平衡、土压平衡、岩石破碎、卵石破碎；非顶管机为空）、`diameter_mm`（口径，可空）
  - `manufacturer`、`model`、`serial_no`、`spec`
  - `ownership`（`owned` 或 `leased_in`）、`purchased_date`
  - `location`（`warehouse`、`project`、`scrapped`）
  - `current_project_id`，约束：`location = 'project'` 当且仅当它非空
  - `storage_note`（库位）、`photo_key`、`remark`、`version`（乐观锁）
- `device_event`（时间线，只增不改）：`device_id`、`event_type`、`ref_type`、`ref_id`、`summary`（中文一句话）、`photo_keys_json`、`operator_userid`、`occurred_at`。

**物资**

- `material`
  - `material_code`（唯一，默认 `WZ-0001`）、`name`、`spec`、`unit`
  - `category`（沿用现有清单的分节：顶进设备、辅助设备、注浆设备、控制照明系统、测量工具、工具、手动工具、劳动保护、施工消耗材料、生活设施、设备维修配件）
  - `kind`：`turnover` 周转、`consumable` 消耗
  - `quantity`（在库数量），带约束 `CHECK (quantity >= 0)`
  - `unit_price`（可空，只用于估算报损金额）、`min_stock`（可空）
  - `storage_note`、`status`、`remark`

规格要落到具体值。现有表格里"DN25/32/40"这种写法在系统里是三条物资。

**库房单**

- `wh_doc`
  - `doc_no`（唯一，`KFD-年月日-序号`）
  - `doc_type`：`opening` 期初、`inbound` 入库、`out` 发往项目、`back` 项目返库、`transfer` 项目间转场、`adjust` 盘点调整、`scrap` 报废、`unscrap` 撤销报废
  - `project_id`（发往、返库的项目；转场的来源项目）、`to_project_id`（转场的目的项目）
  - `project_kit_id`（按清单发货时带上）
  - `counterparty`（供应商，自由文本）、`handover_name`（领料人，对应现有表尾的签字栏）、`remark`、`photo_keys_json`
  - `stocktake_id`、`reverses_doc_id`（冲销哪张单）
  - `operator_userid`、`occurred_at`、`client_request_id`（唯一，幂等用）
- `wh_doc_line`
  - `doc_id`、`device_id`、`material_id`，约束：两者恰好一个非空
  - `quantity`（正数；设备行固定为 1）
  - `outcome`（返库单的物资行用：`returned` 退回、`lost` 丢失或损坏；其他情况为 `normal`）
  - `stock_delta`（在库数量的变化，带符号；设备行为 0）、`balance_after`（物资行的变更后在库数）
  - `project_id`、`project_delta`（该项目名下数量的变化，带符号；只有周转件才非零）
  - `usage_meters`（顶进距离）、`soil_type`（土质）：返库单里顶管机的行可填
  - `note`

项目名下某周转件的在场数 = 该项目该物资所有 `project_delta` 之和。发往项目加，退回减，报损减，转场时来源项目减、目的项目加。消耗类物资发出即视为用掉，不记在场数，没用完的可以退回。

**项目配套清单**

- `kit_template`：`name`（例如"土压平衡""泥水平衡"）、`machine_type`、`remark`、`status`。
- `kit_template_line`：`template_id`、`section`、`sort_order`、`line_kind`（`device`、`material`、`text`）、`device_category_id`、`name_text`（品名）、`spec_text`（规格提示，可空）、`unit`、`default_qty`、`note`。模板行只定品名，不定具体规格，因为规格随管径变。
- `project_kit`：`kit_no`（`PT-年月日-序号`）、`project_id`、`title`（例如"DN1200 第二套"）、`template_id`、`status`（`draft`、`submitted`、`confirmed`、`closed`）、创建人、确认人、时间、备注。
- `project_kit_line`：同模板行的字段，另有 `planned_qty` 和 `source`（`warehouse` 库房发、`site_purchase` 现场采购、`rental` 租赁、`on_site` 现场已有）。

三种行：

- `material`：指向一条物资，数量由库房单回填。
- `device`：指向设备类别并写明规格要求（例如"机头土压 2400"），发货时扫到具体哪台。
- `text`：物资档案里没有的东西，只作备忘，不参与数量统计。

清单上不存实发数。"已发、已退、报损、在场"都从库房单按项目汇总算出，所以一个项目有多份清单时，计划数相加，实发数只有一份。

**任务**

- `wh_task`
  - `task_no`（唯一，`KFR-年月日-序号`）
  - `kind`：`inspection` 检查、`maintenance` 维修、`servicing` 保养、`other`
  - `source`：`return` 返库自动生成、`followup` 检查不合格自动生成、`manual`
  - `device_id`（可空）、`title`、`description`
  - `systems`（维修涉及的系统，多选：液压、电气、传动、其他）
  - `blocking`（1 表示未完成前设备不能发出；检查和维修默认 1，保养和其他默认 0）
  - `required_photo_count`、`due_date`、`assignee_userid`、`created_by_userid`
  - `status`：`todo`、`submitted`、`done`、`cancelled`
  - `result`（检查任务用：`pass`、`fail`）
  - `result_note`（执行人写的简报）、`review_note`（库管退回时写的要求），两个字段分开
  - `supplement_round`、`parent_task_id`、`origin_doc_id`
  - `submitted_at`、`done_at`、`done_by_userid`、`cancel_reason`、`version`
- `wh_task_photo`：`task_id`、`file_key`、`uploaded_by_userid`、`deleted_at`。照片上传即落库，不等提交。

**盘点**

- `stocktake`：`stocktake_no`（`PD-年月日-序号`）、`scope`（`material`、`device`、`all`）、`status`（`counting`、`done`、`cancelled`）、发起人、完成人、时间、备注。
- `stocktake_material_line`：`stocktake_id`、`material_id`、`counted_qty`（可空）、`book_qty`（录入实盘数那一刻的账面数）、`note`、`counted_by_userid`、`counted_at`。
- `stocktake_device_line`：`stocktake_id`、`device_id`、`expected`、`found`（空、1、0）、`note`、`scanned_by_userid`、`scanned_at`。

**资料**

- `doc_file`
  - `title`、`file_name`、`file_key`、`file_size`、`content_type`
  - `doc_category`：`cert` 合格证、`report` 检测报告、`params` 技术参数、`manual` 说明书、`maintenance` 保养维修、`other`
  - 归属：`device_id`（单台）或 `device_category_id`（整个类别），都为空表示通用
  - `valid_until`（证书有效期，可空）
  - `supersedes_id`（替换了哪个旧文件）、`uploaded_by_userid`、`deleted_at`
  - 镜像字段：`wedrive_fileid`、`mirror_status`（`pending`、`syncing`、`synced`、`failed`、`skipped`）、`mirror_error`、`mirror_attempts`、`mirrored_at`
- `doc_share`：`token`（唯一）、`doc_file_id`、`expires_at`、`created_by_userid`、`revoked_at`、`access_count`。对外分享链接。
- `wedrive_folder`：`path`（唯一）、`fileid`。缓存已在微盘建好的目录。

### 6.2 设备状态是算出来的

`device` 表不存"状态"。显示用的状态由位置和未完成任务算出，全系统只用一个函数：

| 条件（从上到下取第一个命中） | 显示 | 能否发出 |
|---|---|---|
| `location = 'scrapped'` | 已报废 | 否 |
| `location = 'project'` | 在项目（项目名） | 否 |
| 在库，有未完成的阻塞维修任务 | 维修中 | 否 |
| 在库，有未完成的阻塞检查任务 | 待检 | 否 |
| 在库，有其他未完成的阻塞任务 | 暂不可用 | 否 |
| 在库，无阻塞任务 | 可用 | 是 |

"未完成"指 `status` 为 `todo` 或 `submitted`。没有任何接口能直接写位置或状态。

设备的累计顶进米数由返库单行上的 `usage_meters` 汇总得到，也不单独存。

### 6.3 写入的原子性和幂等

所有多步写入用 `runAtomicBatch`，并遵守三条规则：

1. **前置条件写成批内断言。** 把"设备在库且没有阻塞任务"这类条件写成子查询，喂给一个非空列。条件不成立时子查询返回空，非空约束报错，整批回滚。实现上用一张永远为空的表 `wh_guard (ok INTEGER NOT NULL)` 承接这些断言，每个批处理的最后一条把它清空。
2. **库存不足靠约束拦。** `material.quantity` 有 `CHECK (quantity >= 0)`，扣减语句违反约束就报错回滚。
3. **幂等靠唯一键。** 客户端在打开表单时生成 `client_request_id`，随单据提交；重复提交撞唯一约束，服务端返回已存在的那张单。

批处理之前先做一次普通查询，用来给出具体的中文错误（"SB-0012 有未完成的返库检查"）。批内断言只负责兜住并发，失败时提示"数据已变化，请刷新后重试"。

同一批里后面的语句要引用刚插入的单头时，用 `client_request_id` 或单号做子查询取它的 ID。单号用现有的 `generateSerial`，撞唯一约束时重试一次。

实现的第一步是写一个测试，证明批内断言失败和约束失败都会让整批回滚。测试用 `node:sqlite` 的真实 SQL 夹具（现有 `packages/api/test/helpers/reimbursement-harness.ts`，抽成通用版）。

## 7. 业务流程

### 7.1 出配套清单

1. 项目负责人或库管选模板和项目，系统按模板生成清单。也可以从同管径的上一个工程复制，这是现在的习惯做法。
2. 逐行改计划数量，标来源（库房发、现场采购、租赁、现场已有），可以加行删行。物资行要在同品名的几种规格里选定一种（例如排泥钢管选 Φ114 还是 Φ80）；从上一个工程复制来的已经选好。
3. 项目负责人提交后通知库管；库管确认。库管自己建的清单直接确认。
4. 工程中途要追加：再建一份清单，标题写"追加"，走同样的流程。这也替代了在群里喊"再发点什么过来"。

模板在 Web 上维护。初始的土压、泥水两套模板从现有表格整理导入。

### 7.2 按清单发货

1. 库管打开已确认的清单，只显示来源是"库房发"的行，默认数量是"计划数减已发数"。
2. 设备行逐台扫码；物资行确认或修改数量；清单外的东西也可以临时加。
3. 提交生成一张 `out` 库房单。一个批处理内：
   - 每台设备断言"可用"，改位置为该项目，写时间线。
   - 每条物资扣在库数量；周转件同时给项目在场数加上。
4. 通知项目负责人（`project.manager_userid`）。

不对着清单也可以直接发货：选项目，扫码或选物资，提交。

设备有未完成的阻塞任务时不能发出。确实要发，库管先取消那个任务并写原因，取消会记入时间线。

### 7.3 项目返库

1. 库管打开"项目在场清单"：这个项目名下的设备和在场数大于零的周转件。
2. 设备逐台扫码。顶管机可以顺手填顶进距离和土质。
3. 周转件逐行填退回数和报损数（丢失或损坏），两者之和不能超过在场数。没用完的耗材填退回数。
4. 提交生成一张 `back` 库房单。一个批处理内：
   - 设备断言在该项目，改位置为在库，写时间线，并为每台设备建一个检查任务（阻塞，默认要 3 张照片，默认派给设置里的"默认检查人"，未设置则派给操作的库管，期限为 2 天后）。
   - 退回的物资加回在库数量；退回和报损都从项目在场数里减掉。
5. 通知被派到任务的人。

只返一台设备时不用打开清单：扫码，点"返库"，确认。

系统上线前就在工地上的东西，系统里没有在场数。这些东西回来时按"入库"登记并注明来自哪个项目。

### 7.4 项目物资结清

项目的物资页是现有那张登记表的自动版，每行显示：计划、已发、已退、报损、在场、首次出库日期、最后退库日期、报损金额（报损数乘单价，没填单价的不算）。

所有设备已离场且周转件在场数全部为零时，项目物资显示"已结清"，清单可以关闭。

### 7.5 项目间转场

设备和周转件不回库直接去下一个项目：`transfer` 库房单，断言东西在来源项目名下，改到目的项目。不动在库数量，不生成检查任务。通知两个项目的负责人。

### 7.6 入库、冲销、期初

- 入库：选物资（可多行），填数量，可填供应商、拍送货单，提交。在库数量增加。新设备不走入库单，在设备台账里新建。
- 冲销：录错了不改不删，库管对那张单点"冲销"，系统生成一张相反的单，原单标记已冲销。一张单只能冲销一次；涉及的设备之后又动过的不能冲销。
- 期初：导入物资清单时带初始数量，生成一张 `opening` 单。导入设备时可以直接标明在哪个项目。

库房单提交即生效，不走审批。

### 7.7 任务

状态线：

- `todo`：待派工（没有执行人）或待执行（有执行人）。
- `submitted`：待确认。
- `done`、`cancelled`。

规则：

- 没有单独的"开始"步骤。任务有了照片或草稿就在列表里显示"进行中"。
- 执行人上传照片即保存，可以删自己的照片，随时离开再回来。
- 提交时：照片总数不少于 `required_photo_count`；检查任务必须选合格或不合格；简报必填；维修任务勾选涉及的系统。
- 执行人本人是库管时，提交即完成。否则进入待确认，由库管"确认完成"或"退回补充"。
- 退回补充：必须写要求（存 `review_note`），任务回到 `todo`，`supplement_round` 加一，已有照片保留。
- 检查不合格：任务完成时自动生成一个阻塞的维修任务，设备显示"维修中"。检查任务本身正常结束。
- 取消：只有库管能取消，必须写原因。取消阻塞任务等于解除设备阻塞，写入时间线。
- 所有状态变更用带 `version` 的条件更新。

设备页把维修任务按系统（液压、电气、传动）分组显示，加上各项目的顶进距离和土质，就是现有那份"维修使用记录表"。

### 7.8 盘点

- 库管发起，选范围（物资、设备或全部）。同一时间只能有一个进行中的盘点。
- 物资：逐项录实盘数。保存时服务端记下当时的账面数 `book_qty`。可以只盘一部分。
- 设备：逐台扫码标记"找到"。
- 完成时：
  - 物资对每个已盘且 `counted_qty ≠ book_qty` 的项，按差额生成一张 `adjust` 库房单，与盘点状态变更在同一个批处理内。
  - 设备只出报告，不自动改位置：账上在库但没找到的，时间线记"盘点未找到"；扫到了但账上在项目的，提示库管补一张返库单。
- 完成后只读。

### 7.9 报废

报废是设备上的一个动作，不是任务。只有经理和超管能做，必须写原因并拍照，生成 `scrap` 库房单。超管可以撤销报废。

## 8. 设备资料库与微盘镜像

### 8.1 上传和查看

- 上传口：Web 拖拽（支持多文件和整个文件夹，一次选定归属和资料类别）和小程序（从聊天记录选文件、相册、拍照）。
- 大文件用 R2 分片上传，经 Worker 中转：初始化、逐片上传（每片 8MB，直接把请求体流式写入分片）、完成。Web 上限 2GB，小程序上限 200MB，都做成可配置。小程序用文件系统接口按位置分段读取文件，再逐片上传。
- 照片这类小文件继续走现有的签名上传流程。
- 文件键前缀：资料 `doc-library/`，任务照片 `wh-task/`，库房单的照片 `wh-doc/`。三个前缀都加入 `packages/api/src/routes/upload.ts` 的受保护前缀，读取一律通过鉴权接口换取短时签名地址。
- 对象读取接口补上 Range 支持（返回 206）。
- 替换文件：上传新文件并指向旧文件，旧文件保留为历史版本，列表默认只显示最新版。
- 查看：
  - Web：PDF 用已有的 `pdfjs-dist` 内嵌预览，图片直接看，视频用原生播放器，Office 文件下载。
  - 小程序：图片预览；PDF 和 Office 下载后用 `wx.openDocument` 打开；视频用 `<video>` 播放签名地址。企微 Windows 端不支持打开文档时提示改用手机或网页。
- 设备页显示这台设备适用的全部资料：单台的、同类别的、通用的，越具体越靠前。
- 任务页带出任务设备的资料，检查和维修任务把保养维修和说明书排在前面。不再有手册绑定规则表。

### 8.2 证书有效期和对外分享

- 合格证、检测报告、检定证书可以填有效期。每日摘要里列出 30 天内到期的。
- 对外分享：库管或资料管理员可以为一个文件生成对外链接，默认 7 天有效，可随时作废，记录访问次数。链接是不可猜测的随机串，不需要登录即可下载这一个文件。这对应现有资料上的"外部可下载"用法。

### 8.3 现有资料迁入

由有权限的人在微盘客户端把文件夹下载到电脑，再用 Web 按文件夹导入：

- "顶管机参数、合格证、检测报告"下每个子文件夹对应一台设备。导入时按文件夹名匹配设备，匹配不到的提示新建设备。
- "设备说明书""设备合格证"里的文件逐个选归属，或先归到设备类别下。
- 在线表格和微文档（例如"顶管机维修使用记录""拆解2200机头顺序"）接口下载不了，需要先在微盘里导出成文件。

约 150 个文件，以 PDF 和图片为主，最大 36MB。

### 8.4 微盘镜像

调研结论（要点见文末附录）：微盘接口按应用身份调用，应用自建的空间可以完全控制；成员手建的空间大概率读不到。因此镜像目标是一个由应用创建的空间。

- 超管在设置页点一次"初始化微盘空间"：创建空间"设备资料库"，把公司根部门加为只读成员，空间 ID 存 `system_config`。
- 目录结构沿用现在的习惯：`设备类别/设备编号 设备名称/文件名`；归到类别或通用的放在 `设备类别/通用/` 和 `通用/` 下。
- 触发：资料新增、替换、改名、删除时发队列消息。
  - 建目录、改名、移动、删除是纯 JSON 接口，由 Worker 经现有的 bridge 代理调用。
  - 传文件内容统一交给 bridge 的一个新接口：Worker 给出短时签名下载地址、access_token、目标目录和回调地址；bridge 流式下载后上传到微盘（10MB 以内直传，否则分块上传，每块 2MB，带累计 SHA1），完成后带 HMAC 签名回调 Worker。
  - 上传时带 `skip_push_card`，不给全员推卡片。
- 状态和重试：`doc_file.mirror_status` 记录进度。每小时的定时任务把 `pending`、失败未满 5 次的、`syncing` 超过 30 分钟的重新入队。
- 遇到微盘调用限额类错误时暂停镜像并通知超管。镜像失败、暂停或未初始化都不影响系统内上传和查看。
- Web 资料列表显示每个文件的镜像状态，提供"重新同步"。

## 11. 接口

统一前缀 `/api/v1`。每个路由文件一个领域，控制在 400 行内，业务逻辑放 service。

- 通用：`GET /warehouse/me`、`GET /warehouse/overview`、`GET|PUT /warehouse/settings`、`GET|POST|PUT /warehouse/device-category`
- 设备：
  - `GET /warehouse/device`（按状态、类别、项目、关键字筛选，分页）

- 配套清单：
  - `GET|POST|PUT /warehouse/kit-template`

  - `GET /warehouse/project/:projectId/holdings`（在场设备和周转件，返库清点用）

## 12. Web 端

菜单"库房"下 8 个页面，全部进菜单：

1. **总览**：待确认清单、待确认任务、待检设备、低库存、最近的库房单。每个数字点进去是对应的筛选列表。

## 17. 我做的决定

这些不是 owner 说的，是我的判断：

1. 以项目配套清单为发货和返库的主线，但不强制：没有清单也能直接发货和返库。

7. 按清单发货时同一物资在清单里有几行会合并成发货单的一行（库房单不许同一物资出现两次）；设备只按类别提示还需几台，具体哪台由库管挑。
8. 企微机器人的设备汇总多了这个项目的清单（不含作废的）和是否已结清。
9. 发货单只有"发往项目"能带清单；带了别的项目的、没确认的、已关闭的清单都会被拒绝；提交途中清单被关闭时整单回滚。

### 阶段 4A（分支 `feat/warehouse-phase4a-doc-library`，2026-11-12）

状态：代码完成，本地验证通过，**未上线**。有迁移 `0097_warehouse_doc_library.sql`（只加 `doc_file`、`doc_share` 两张表和 5 个索引），合并前要先在生产上跑。计划 `docs/superpowers/plans/2026-11-12-warehouse-phase4a-doc-library.md`。小程序的三个新页面只在 node 里跑过流程测试、用静态页看过版式，没有在开发者工具和真机上跑过；`wx.downloadFile`、`wx.openDocument`、视频播放、分片读文件只能真机验证。

和设计稿不一致或设计稿没写、定下的地方：

1. 阶段 4 拆成 4A（系统内的资料库）和 4B（微盘镜像）。`doc_file` 没有镜像相关的列，也没有 `wedrive_folder` 表，4B 再加。
2. 设计稿说上传签名的问题「已单独立项」，实际没有单独的计划，放在 4A 的第一步做了：签名分用途（`get` / `put`），下载地址不能再用来覆盖文件。部署瞬间还没用掉的旧签名地址会失效（最长 15 分钟，重新打开页面即可）。
3. 对象接口支持 `Range`（206、416），所有前缀都生效；强制附件下载和 `nosniff` 只对 `doc-library/`、`wh-task/`、`wh-doc/` 三个前缀生效，这三个前缀同时加入受保护前缀。别的前缀的回包头不变。
4. 传分片的请求不带登录态，靠初始化时签发的上传令牌（文件键、分片上传 ID、文件名、大小、类型、上传人、24 小时有效，用 `UPLOAD_SIGNING_SECRET` 签名）。不建上传会话表。令牌失效返回 403 而不是 401（小程序的请求层见到 401 会把人登出去）。
5. 分片固定 8 MiB，小文件也走这一条路。每一片必须正好是它该有的大小；完成时核对拼好的对象大小，不对就删掉对象、不写记录。完成请求可以重发：按文件键认出已经写过的记录，原样返回。
6. 存储临时出错（R2 的内部错误、未说明的错误）时，传分片和完成请求返回 500，客户端重传这一片或只重发完成请求；不说成「上传已失效」。本地联调时真的遇到过一次。
7. 替换走同一个完成接口，带 `supersedes_id`。替换或删除时，文件上还有效的对外链接同批作废。只有最新版能改、能删、能生成对外链接；删掉最新版后上一版重新成为最新版。
8. `doc_file` 有 `version` 列，改资料信息时防并发覆盖。
9. `POST /upload/sign` 不接受 `doc-library` 类别；`POST /upload/sign-download` 不给 `doc-library/` 的键签名。资料的查看地址只从 `GET /doc-library/file/:id/url` 拿（15 分钟有效；带 `filename=` 决定下载时的名字，带 `download=1` 强制下载，这两个参数不在签名里）。
10. 对外链接：32 个随机字节的令牌；有效期 1 到 30 天，默认 7 天；公开接口直接把文件流出去（带 Range，一律当附件）。令牌不对、过期、作废、文件已删除或已被替换，一律 404「链接已失效」，不说原因。同一来源每分钟 30 次。请求日志里令牌写成 `***`。Web 上显示和复制的链接走网页用的那个入口（生产上是 `api-relay`）。
11. 扩展名白名单 24 个（计划里的 23 个加 `ofd`）；类型由服务端按扩展名定。Web 和服务端的大小上限 `warehouse.doc_max_mb`（默认 2048），小程序 `warehouse.doc_max_mb_miniapp`（默认 200），都存在 `system_config`。
12. 跨域配置加了允许 `Range` 请求头、暴露 `Accept-Ranges`、`Content-Range`、`Content-Length`、`Content-Disposition`：Web 和 API 不同源，pdf.js 要读到这几个头才会分段取。
13. Web 上的文件和路由叫 `doc-library`（`api/wh/doc-library.ts`、`views/wh/doc-library/`、`/wh/doc-library`），不叫 `doc` / `docs`：`api/wh/doc.ts` 和 `views/wh/doc` 已经是库房单。
14. PDF 预览用 pdf.js 逐页画；没有带中文 CMap，用了没内嵌中文字体的 PDF 在页面里可能缺字，「在新窗口打开」和「下载」不受影响。HEIC 和 SVG 在 Web 上只给下载。
15. 文件夹导入：只有一个总文件夹、它自己对不上设备、下面还有子文件夹时，按子文件夹分组；总文件夹本身对得上设备或者里面只有文件时，整个文件夹一组；一次拖进来几个文件夹各自一组。编号匹配不分大小写，几个编号都包含时取最长的；名称对上不止一台不猜。资料类别先看文件名，再由近到远看文件夹名。更深一层的文件标题带上子文件夹名。导入时不问有效期。
16. 上传队列（Web）：同时传 2 个；一片传不上自动重传 3 次，中间等 1 秒；完成请求没拿到回应或服务端 5xx 时留着分片，重试只重发完成请求。
17. 小程序上只做看和传；改、删、替换、对外链接、文件夹导入在 Web 上。小程序的文件地址照接口给的用（直连），和别的附件一样，不经中继。
18. 小程序怎么打开看扩展名：图片预览，`mp4`、`mov` 在页面里放，`pdf`、Word、Excel、PPT 下载后用系统查看器，其余「请在电脑上打开」。文档超过 50 MB 打开前先问。
19. 小程序上传：一片一片用 `readFile` 的 `position`、`length` 读（客户端不认这两个参数时退回整读再切），分片请求的超时是 180 秒（`uploadBinary` 多了可选的 `timeout`）；完成请求失败后，除非上传本身废了（403，或 400「文件不完整」），分片都留着，改好表单再点只重发完成请求。
20. 设备卡片上的资料份数、任务详情的适用资料取不到时不提示、不影响页面。
21. 列表里证书 30 天内到期标橙、已过期标红；主动提醒放在阶段 5 的每日摘要里。

## 附录：微盘接口要点

来源是企微开发者文档的微盘章节（`developer.work.weixin.qq.com/document/path/<编号>`），2026-11-11 查阅。标"未验证"的没有用真 token 试过。

- 2022-12-01 起微盘接口按应用身份调用，`userid` 参数已废弃（更新日志 93221，错误码 40203）。
- 调用前提：管理端"协作 → 微盘 → API"把应用加入可调用接口的应用（93654）；用应用自己的 secret 取 token；需要可信 IP。
- 接口都是 `POST /cgi-bin/wedrive/<名称>`：`space_create`（93655）、`space_acl_add`（93656）、`file_list`（93657）、`file_upload`（97880，base64，上限 10MB）、`file_upload_init/part/finish`（98004，每块固定 2MB，带累计 SHA1，最大 20GB）、`file_download`（97881）、`file_create`（97882，建文件夹）、`file_rename`、`file_move`、`file_delete`（97883 到 97885）。
- `file_download` 返回的下载地址 2 小时有效，且必须带接口返回的 cookie，浏览器和小程序不能直接用。
- 只能下载普通文件，微文档和表格下载不了。
- 应用空间里通过接口添加的成员只能下载或预览；能在客户端管理空间的"应用空间管理员"最多 3 人，不支持部门。
- 变更回调只覆盖应用创建的空间和应用上传的文件（97899、97900），没有增量接口。
- 自建应用能否读成员手建的空间：文档没有明说；有开发者实测 `file_list` 返回 640008 无权限；也没有把应用加进已有空间的办法。未验证。
- 错误码表里有"免费版 1000 次/企业/月"（640019、640035），现行概览不再提。是否仍生效未验证。
- 小程序没有打开微盘文件或目录的接口，只有文件选择器。
