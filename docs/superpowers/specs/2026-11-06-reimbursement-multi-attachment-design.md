# 报销多附件统一与详情页改版 设计

日期：2026-11-06 · 状态：待 owner 批准

样稿：[2026-11-06-reimbursement-detail-mock.html](2026-11-06-reimbursement-detail-mock.html)（owner 选定的 C 版，含三种真实情况和全部说法）

## 1. 为什么要改

三个问题连在一起：

1. **识别不全。** 网页传了 11 个附件，AI 只识别前 4 个（信封 323）。不是 4 个的硬上限：提交请求在循环里逐个建识别任务，请求中断后后面的就没了。全部 260 次提交有 4 次这样中断（299、322、323、324）。
2. **两端不一致。** 网页一次选一个但能传多个，小程序每次只能传一个，电子发票名义上一单一票。实际 172 张电子发票单里已有 44 张是多附件。
3. **详情页看不懂。** 状态重复 3 次，操作按钮在最底部，识别结果是一段文字且对不上文件。owner 原话：要「一个简单且清晰的结论，以及提醒我该做什么，现在版面太复杂，而且像是拼接出来的一样」。

调查证据见 `doc/开发记录.md` 的 2026-11-06 20:50 条目。

## 2. 目标、非目标、不能发生的事

**目标**

- 提交后每个有效附件最终都有识别结果，或明确显示失败。
- 网页和小程序的上传规则相同，都能一次传多个。
- 打开详情页，第一眼看到一句结论和该做什么；办公室能边看原件边核对。

**非目标**

- 不拆分「一个文件里的多张发票」（合并 PDF、一张照片拍多张收据）。仍算一条记录，系统提示差额或算不出合计，由人看原件。
- 不提高 AI 关卡的附件读取上限（`task-runner/runner/evidence.py`）。
- 小程序不做办公室核查，也不做左右对照。
- 不改批次、审批、打款流程。

**不能发生的事**

- 提交等待 AI 或被 AI 拖慢（`CLAUDE.md`：AI 任务不能阻塞提交）。
- 附件没识别完却显示已完成，或没读全时说「金额不一致」。
- 把 AI 的猜测写成结论：费用合理性审查只能打「留意」标记，不进入第一行结论。
- 现有办公室功能丢失（第 7.3 节逐项列出去向）。
- 提审期间旧版小程序不能用。
- 改坏批次 AI 关卡读取的 `silent_review_result` 字段（`services/ai-slot.ts:314`、`routes/reimbursement.ts:1971` 读 `ai_reasonability_summary` 和 `summary`）。
- 费用合理性审查失败或没跑完时拦住复核通过。

## 3. owner 已定的事

- 取消电子发票一单一票，两端统一多附件。
- 详情页用 C 版「边看边核」：上方结论和按钮，下方左边选发票，右边显示原件和识别内容。
- 第 6 节的结论和提醒说法。
- 左列第一行是「报销信息」；新建时右边默认显示要填的信息，办公室打开时默认显示发票，优先有问题的，其次金额最大的。
- 多文件可一次选择或拖入，每个文件单独显示进度，失败的单独重试。
- 报销金额默认等于已识别的票面合计，可以手动改。
- 拆单、重新识别、切换通道、换绑信封、废止收进「更多」。
- 格式只留 PDF、JPG、PNG（生产生效附件只有 pdf 257、jpg 231、png 12）。
- 小程序这次一起改，只面向申请人：同样的结论和提醒，每个文件显示状态和识别金额。
- 上线顺序：先修提交，再统一多附件，最后换详情页。

## 4. 提交与识别链路

### 4.1 现状

- `routes/reimbursement.ts` 提交路由（5192-5373）先把状态改成 submitted，再在请求内调 `enqueueEnvelopeAiAudit`（840-980）。中断后状态已变，任务只建了一部分，幂等行一直 pending。
- `createInvoiceReviewTasks`（509-571）先建任务后写识别行，不原子（324 有孤儿任务）。
- `syncEnvelopeAuditState`（982-1331）只在 `GET /:id` 和 `/ocr-status` 触发，所以 21 单 30 行识别结果要打开页面才更新。它只看识别行，不对比附件数，所以「建了 4 个」就算完成；不排除已删附件；第 1168 行 `COALESCE` 让结论冻结在第一次打开时。
- `reimbursement_anomaly` 和 OCR 同时创建，拿不到识别结果，结论写着「发票号码均为空」。
- 已退回的单点「重新提交」其实什么都不做：路由对 submitted 直接返回 `already_submitted`（5248），`precheck_status` 还是 supplement。现在只有再传附件才会让单子回到办公室（`PUT /:id` 触发审查时把 `precheck_status` 改成 pending）。
- `requeueTimedOutTasks`（`services/cron-jobs.ts:38`）会把有重试额度的 timeout 任务重新排队，但同步已把识别行标成 failed，之后又跳过 failed 行（1021）。重试成功也读不到结果，页面一直显示失败。
- `duplicate_check_status` 由三处写入：`applyDuplicateChecks` 末尾写 completed（832），同步按识别进度写 pending 或 completed（1167），合理性审查失败写 failed（1325）。所以复核通过等的是识别结束；合理性审查还在跑时不拦，但它失败会拦。

### 4.2 新流程

把识别相关逻辑从路由移到 `services/reimbursement/`（队列和 Cron 都要调用，路由文件已超过 6000 行）：

- `ensureInvoiceReviews(env, envelopeId)`：当前轮次里，每个有效附件没有识别行就建。任务和识别行用 `DB.batch()` 一起写入（生产 D1 不支持 `runInTransaction`，见记忆 `d1-runintransaction-no-rollback`）。重复调用安全。建完唤醒 runner，避免等下一轮 Cron。
- `syncEnvelopeAuditState`：修复后见 4.3。
- `ensureAnomalyReview(env, envelopeId)`：见 4.5。

调用时机：

| 时机 | 做什么 |
|---|---|
| 添加附件 | `ensureInvoiceReviews`。草稿也识别，这样才能给出已识别金额和默认报销金额 |
| 点提交 | 请求内只做权限和状态检查、查重、更新状态、发事件 `REIMBURSEMENT_ENVELOPE_SUBMITTED`、完成幂等。发事件失败只记日志，不让请求失败 |
| 队列消费该事件 | `ensureInvoiceReviews`，再 `syncEnvelopeAuditState` |
| `TASK_COMPLETED`（`ocr_extract`、`reimbursement_anomaly`，`biz_type = reimbursement_envelope`） | `syncEnvelopeAuditState` |
| Cron 每 2 分钟 | 对账，每次最多处理 10 单：`submitted`、`received`，以及 24 小时内有新附件的草稿；补缺失的识别行，并同步任务已结束但识别行未更新的单。永不抛出 |
| `GET /:id` | 继续同步，作为最后一层兜底 |

更老的草稿不补识别，避免一上线就替废弃草稿跑 AI。

**防重复：** 给 `reimbursement_invoice_review(envelope_id, attachment_id, review_round)` 加唯一索引。现有代码在 failed 行上重建时会插入同轮第二行，生产可能已有重复，迁移前要查，有重复先清理；查生产要 owner 同意。修复后失败重试改为更新原行。

**提交卡住：** 幂等行为 pending 时，如果信封已是 submitted，直接补完成并返回 `already_submitted`。否则被中断的同一个请求重试会永远得到 409。

### 4.3 识别状态和合计

每个附件的状态由服务端算出，随详情接口返回：

| 状态 | 条件 | 页面显示 |
|---|---|---|
| `recognizing` | 没有识别行，或识别行未结束 | 识别中 |
| `recognized` | 已完成且金额大于 0 | 金额 |
| `not_invoice` | 已完成、无金额，且 `document_type` 不是发票 | 不是发票，并显示读到的内容（`raw_text_summary`） |
| `no_amount` | 已完成、无金额，其他情况（含历史数据） | 没读到金额 |
| `failed` | 任务 failed，或 timeout 且重试用完（`retry_count >= max_retries`） | 没读出来 |
| `not_recognized` | 已过 received 的历史单没有识别行 | 未识别 |

- timeout 但还有重试额度的算 `recognizing`。同步也要重新检查 failed 行，任务后来完成了就写回结果。
- OCR 输出增加 `document_type`（`invoice`、`receipt`、`other`，`task-runner/runner/executor.py:415`）。提示词改动要同步到 `.cf-runner-container` 并部署 runner。没有这个字段的历史数据按 `no_amount` 算，不猜测。
- 每个附件取当前轮次最新一行；已删附件不计入。
- `ocr_status`：有附件处于 `recognizing` 就是 pending。
- **合计：** `extracted_total` 只加 `recognized`。只有所有附件都是 `recognized` 才比较差额，否则不说金额不一致（现在把空值当 0，327 会被误报）。金额为 0 视同没读到。
- **结论不再冻结：** 每次同步覆盖 `silent_review_result` 的 `summary`、`invoice_review`、`amount_consistency`，保留 `ai_reasonability`。JSON 结构不变。

### 4.4 查重

- 点提交时要当场问「是否坚持提交」，所以查重留在请求内。草稿已有识别结果，提交时把每张发票的结果也算进去（现在只比信封上的一个发票号）。
- **同一单内重复：** 现在只比别的单（`envelope_id != ?`，`routes/reimbursement.ts:595`），同一张传两次查不出，合计多算。新增 `match_type = 'same_envelope'`，风险 high，`evidence_json` 记两个 `attachment_id`。
- `reimbursement_duplicate_check` 的 `evidence_json` 都记 `attachment_id`，页面才能标出是哪张。
- 所有查重（唯一编号、发票号加日期、二维码、金额接近）都只和已提交及之后的单比，不含 draft、unregistered、cancelled、deleted，也不比已删附件。草稿现在也识别，而申请人删不掉自己的废弃草稿（废止和删除只有超管能做），不排除的话会被旧草稿拦下。两张草稿有同一张发票时，先提交的不报，后提交的报，结果是对的。实现时要核对拆单流程（`/:id/split`）不受影响。
- `applyDuplicateChecks` 里按 `file_key` 查重永远查不出（key 含 uuid）。不修，改靠发票号。

### 4.5 费用合理性审查

- 只在信封已提交、所有附件的识别都结束、且至少一张识别成功后才建任务。全部失败时没有内容可审，等重新识别后再跑。
- **不拦复核：** `duplicate_check_status` 只由识别进度决定，还在识别为 pending，结束为 completed。提交时在改状态的同一条 UPDATE 里设成 pending；`applyDuplicateChecks` 不再写 completed（832）；合理性审查失败不再写 failed（1325）。`/:id/precheck` 等待时改为调 `ensureInvoiceReviews`，不再看合理性任务（4047）。审查失败时页面只是没有「留意」，办公室可以在「更多」里重跑。
- 用附件和识别任务算一个指纹写进 payload。指纹和最新一次相同就不重复建；增删附件或重新识别后指纹变了才重跑。草稿不跑。
- payload 增加 `invoices[]`（`attachment_id`、文件名、销售方、购买方、发票号、日期、金额、`document_type`）。
- 新提示词（`routes/admin.ts:166` 默认值，并用迁移更新数据库模板，模板优先）：
  ```json
  {"risk_level":"low|medium|high","summary":"","anomalies":[{"attachment_id":0,"level":"low|medium|high","reason":""}],"recommendation":""}
  ```
  去掉提示词里已无意义的「附件分类是否正确」，以及未填充的 `{{items}}`、`{{total_amount}}`。
- 读取时做容错：低/中/高/待核验 映射到枚举，认不出的不显示。不再出现「风险等级：未标记」。
- 只有带 `attachment_id` 且 `level` 为 medium 或 high 的才在该发票上打「留意」。旧模型 118 单有 111 单是中风险，整单风险等级没有信号，不用它决定结论。

### 4.6 重新提交

`POST /:id/submit` 在 `status = submitted` 且 `precheck_status` 为 supplement 或 rejected 时：把 `precheck_status`、`verification_status` 改回 pending，调 `ensureInvoiceReviews` 和合理性审查，写审计日志 `reimbursement.envelope.resubmit`，返回 `resubmitted: true`。查重规则相同。其他 submitted 情况仍返回 `already_submitted`。

办公室驳回和要求补充都把状态改回 submitted（4189），批次驳回把状态改回 received、`batch_id` 不清（`queue-handler.ts:164`）。这些流转不变。

旧客户端用 `PUT /:id` 传附件时，继续把 `precheck_status` 改回 pending，否则旧版没有办法把单子交回办公室。

## 5. 多附件规则

服务端统一检查，两端只做提前提示。

| 规则 | 值 |
|---|---|
| 格式 | pdf、jpg、jpeg、png，按文件名后缀，不分大小写 |
| 数量 | 一单最多 30 个有效附件（目前最多 16 个） |
| 大小 | 单个不超过 20MB，用 `env.FILES.head` 取实际大小，不信客户端 |
| 文件 | `file_key` 必须是 `reimbursement/` 前缀且 R2 中存在（现在可以绑定任意 key） |
| 重试 | 同一单绑定相同 `file_key` 返回已有记录 |
| 谁能添加 | 沿用现有规则：draft、unregistered、submitted 为申请人和办公室角色，received 只有办公室角色 |
| 谁能删除 | draft、unregistered，以及 `precheck_status` 为 supplement 或 rejected 的 submitted |
| 复核失效 | 已复核通过（`precheck_status = approved`）的单增删附件，改回 pending，退出成批候选（候选条件见 1714）。supplement、rejected 不改，等申请人点重新提交 |

接口：

- 新增 `POST /:id/attachments`，body `{attachments: [...]}`：检查规则、写入、`ensureInvoiceReviews`。不开新轮次、不跑合理性审查。
- 新增 `POST /:id/attachments/:attachmentId/rerecognize`：只重跑这一张，更新原识别行。只对 `failed` 状态的附件，已复核通过的单不能用。申请人可以用于自己的草稿和被退回的单，办公室角色可以用于 submitted 和 received。
- `POST /`、`PUT /:id` 带附件时用同样的检查和 `ensureInvoiceReviews`，不再调整轮审查。
- `/electronic-upload` **保持现状只加格式检查**，新版两端不再调用，旧版小程序继续能用（它自己的「替换或另建」弹窗也还在）。旧版退出后再删路由。
- `POST /:id/trigger-anomaly-check` 保留，界面上叫「全部重新识别」，开新一轮。
- `POST /:id/void` 增加 `reason`，存到新字段 `void_reason`。新页面的废止弹窗必填。现在废止不收原因，历史单和批量废止没有原因时，页面只显示「不再流转。」

上传流程（两端相同）：每个文件独立走「签名、传 R2、绑定」。网页同时 3 个，小程序同时 2 个。文件名和大小都和已有附件相同的跳过并提示。新建时项目是必填，所以选好项目（实物信封还要识别号）才能传；第一个文件传完时自动创建草稿。

去掉附件类型选择，新附件写 `invoice`，由 `document_type` 判断实际类型。`attachment_type` 字段保留。

## 6. 结论和提醒

服务端用一个纯函数算好，随 `GET /:id` 返回，两端说法完全一样：

```ts
guidance: {
  applicant: Guidance;
  office: Guidance | null; // 无办公室权限或不能自审时为 null
}
// Guidance: { tone: "normal" | "warn" | "done"; headline: string; next_step: string; note: string | null; actions: GuidanceAction[] }
```

网页的工作台视图和小程序用 `applicant`，其他网页入口有 `office` 就用 `office`。草稿和未登记的单 `office` 为 null，所有人都看 `applicant`，因为办公室角色这时也能直接编辑和提交。`actions` 是固定的键名（`verify`、`mark_mismatch`、`precheck_approve`、`precheck_supplement`、`precheck_reject`、`submit`、`resubmit`、`rerecognize_failed`、`scan_register`、`view_batch`、`open_batching`），第一个是主按钮，客户端映射到现有处理函数。路由权限检查不变，`guidance` 不替代授权。

「还在上传」只有客户端知道，这一条由客户端覆盖显示：「还有 N 张发票没传完」「传完确认金额，就可以提交了。」，提交按钮不可点。

### 所有人

| 情况 | 结论 | 该做什么 | 按钮 |
|---|---|---|---|
| received，所在批次被驳回（`batch_id` 非空且批次 `status = rejected`，优先于上面两张表） | 所在批次被驳回 | 办公室到批次详情处理；申请人现在不用做什么。 | 查看批次 |

## 11. 由 Claude 定的事，请你过目

这些没有和你逐条确认：

1. 一单最多 30 个，单个不超过 20MB。20MB 是估的，小程序没传文件大小，线上记录不全。
2. 草稿阶段就识别（金额默认值需要），但合理性审查提交后才跑。
3. 提交不等识别完。金额为空时界面不让提交，要等识别完或手动填。
4. 结论的优先级：重复、混入电子发票、识别失败、还在识别、没金额、差额、正常。一次只说最优先的一件，其他的在文件行上看。
5. 补了样稿没有的情况：办公室「正常」「已标记异常」「已退回等申请人」「已复核待成批」「已签收但有重复或电子发票」，申请人「未绑定识别号」「混入电子发票」「识别失败」「没金额」「核查发现问题」「已复核」「已签收」，所有人「所在批次被驳回」。说法在第 6 节。
6. 「把发票拖进左边」改成「把发票传上来」，因为小程序不能拖。
7. 同一单内重复算 high，办公室复核通过时会被拦下（要申请人坚持提交或财务填理由），和其他重复一致。
8. 提交时查重也算每张发票，申请人看到「坚持提交」确认的次数可能变多。
9. 被退回后才能删附件，已提交未退回的只能加不能删（和现在一样）。
10. 新增 OCR 的 `document_type`，要部署 runner。这样才能说「手写收据」；否则只能说「没读出金额」。
11. 表单没有失焦自动保存，改动后出现「保存」按钮。
12. 旧版小程序的 `/electronic-upload` 保留，一单一票在旧版退出前对它还有效。
13. 费用合理性审查不拦复核通过，只有识别没结束才拦。现在它失败时会拦，我认为 AI 故障不该挡住办公室。
14. 查重不和草稿比。两张草稿有同一张发票时，先提交的不报，后提交的报。
15. 已复核通过的单增删附件后复核失效，要重新复核（和现在一致）。
16. 申请人只能重新识别失败的那几张，办公室也一样；要全部重跑才走「全部重新识别」。
17. 废止新增必填原因，因为你确认的说法要显示废止原因，而现在没有地方存。
18. 不放开切换通道权限。实物信封混入电子发票时，申请人看到的是「新建一张电子发票报销，或联系财务切换通道」。
