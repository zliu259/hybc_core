# 企业微信智能机器人工具优先架构开发计划

> **执行要求：** 进入开发时按任务包顺序推进。每个任务包先写测试，再实现，再跑验证。第一阶段只开放只读工具和群消息推送，不开放写入工具。

**目标：** 建设企业微信智能机器人可调用的项目数据 API/MCP 工具层，并用企业微信群机器人 Webhook 完成项目日志主动推送。

**架构：** 工具核心服务独立于协议适配层；HTTP API 与后续 MCP 入口共用同一套工具注册表和数据读取逻辑。日志推送走现有 event-bus 与 Cloudflare Queue，Webhook 只作为通知出口。

**技术栈：** Cloudflare Workers + Hono + TypeScript + D1 + KV + Queue；Web 使用 Vue 3 + Element Plus + TypeScript；企业微信出口继续复用 Azure bridge。

## 1. 开发前准备

### 1.1 企业微信租户验证

必须先完成以下验证，再进入代码实现：

- 在企业微信后台确认智能机器人支持的工具接入形态：HTTP API、MCP，或两者均支持。
- 记录智能机器人调用工具时可配置的认证方式：固定 token、签名、OAuth 或其他。
- 记录工具调用请求是否携带 `bot_id`、`group_chat_id`、`caller_userid`、消息上下文。
- 在内部群创建群机器人 Webhook，按 `91770` 文档验证 `text` 与 `markdown` 推送。
- 在目标外部群验证是否支持群机器人 Webhook。若不支持，外部群第一阶段不做自动 Webhook 推送，保留客户群群发 fallback。
- 确认当前 Azure bridge 是否需要代理群机器人 Webhook。若 Webhook 不要求可信 IP，可由 Worker 直接发；若存在出口限制，则经 bridge 代理。

产出记录：

- 将验证结论写入 `doc/开发记录.md`。
- 若企业微信实际协议和 `doc/企业微信智能机器人工具优先架构设计.md` 冲突，先修订设计文档再开发。

### 1.2 环境变量与密钥约定

新增环境变量建议：

```text
WECOM_BOT_TOOL_TOKEN=智能机器人工具调用固定 token
WECOM_TOOL_WEB_BASE_URL=Web 管理端基础地址，用于生成详情链接
WECOM_GROUP_WEBHOOK_PROXY_MODE=direct|bridge
```

KV 密钥引用约定：

```text
wecom:group-webhook:<secret_ref> = https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=...
```

不得把真实 Webhook URL 写入 D1 明文字段。

### 任务包 2：项目群绑定服务

**目标：** 后端支持项目绑定企业微信群、智能机器人和推送 Webhook secret 引用。

### 任务包 5：日志事件与群机器人 Webhook 推送

**目标：** 管理员日志新增/更新/外部日志采纳后，自动向绑定群推送通知。

**文件：**

- Create: `packages/api/src/services/wecom-message-push.ts`
- Create: `packages/api/src/services/wecom-message-push.test.ts`
- Modify: `packages/api/src/services/event-bus.ts`
- Modify: `packages/api/src/queue-handler.ts`
- Modify: `packages/api/src/routes/log.ts`
- Modify: `packages/api/src/services/external-log-audit.ts`

**事件类型：**

- `MANAGER_LOG_CREATED`
- `MANAGER_LOG_UPDATED`
- `EXTERNAL_LOG_ADOPTED`

**推送规则：**

- 业务 API 只发布事件，不同步调用 Webhook。
- Queue 消费时读取 `project_wecom_bot_binding` 中 `push_enabled = 1` 的绑定。
- Webhook URL 从 KV secret ref 读取。
- 第一期只发送 `markdown`，必要时降级 `text`。
- 成功、失败、跳过都写入 `project_wecom_push_event`。
- 同一日志同一绑定同一事件类型需要幂等，避免重复推送。

**测试要求：**

- 创建日志后发布 `MANAGER_LOG_CREATED`。
- 更新日志后发布 `MANAGER_LOG_UPDATED`。
- Queue 消费成功时调用 fetch，payload 符合 91770 Webhook 格式。
- KV 缺失 Webhook 时记录 failed，不影响其他绑定。
- 重复事件不会重复写入 sent。

**验证命令：**

```bash

npm run test -- src/services/wecom-message-push.test.ts src/routes/log.test.ts
npm run typecheck
npm run lint
```

## 5. 不进入第一阶段的事项

- 不做写入工具。
- 不让机器人直接修改里程、日志、设备、审批。
- 不接入财务、报销、合同、收款数据。
- 不做复杂卡片、文件、图片推送。
- 不把智能机器人问答接入 AI Slot。
- 不绕过现有企业微信 bridge 与 Queue 基础设施。

---

## 6. 开发顺序建议

1. 先完成任务包 0，冻结企业微信能力边界。
2. 任务包 1-3 可连续实现，形成工具核心。
3. 任务包 4 暴露 HTTP 工具入口，先让智能机器人可调用。
4. 任务包 5 接日志推送，不依赖 MCP。
5. 任务包 6 做 Web 配置面板。
6. 任务包 7 根据租户能力决定是否上线 MCP。
7. 任务包 8 做真实群联调和发布门禁。

这个顺序保证即使 MCP 暂时不可用，也能先通过 HTTP 工具和群 Webhook 完成可用闭环。
