# 库房系统升级架构设计

## Scope（范围）

本文档定义库房系统升级的目标架构，仅覆盖业务架构、领域模型、流程约束、状态机、读模型与文档同步要求，不涉及代码实现、数据库 DDL、接口字段级协议或页面视觉细节。

本次设计重点覆盖：
- 顶管机组合资产模型（机壳 / 机芯 / 操作台）
- 改装、拆解、回收、报废的业务语义
- 出入库与返库检查/保养闸门
- 统一任务中心
- 项目级运输预算、预付款与运费归集
- 可用资产调度台（available now / available after modification）

## Background and Goals（背景与目标）

当前仓库与资产体系已经具备 `AssetType / TrackedAsset / tracked_asset_event / stock_order / project_equipment_plan` 等通用基础，但尚未原生表达“组合资产 / 父子部件关系 / 时序装配关系 / 顶管机专项改装语义”。

本次升级目标不是推翻现有资产仓库基线，而是在其上增加顶管机专项能力，并把如下业务问题讲清楚：
- 同一机芯可以在生命周期内匹配不同机壳，但 service life 仍跟机芯走
- 某些项目会导致机壳留在地下，只能回收机芯
- 主要设备出库前必须完成维护，返库后未检查前不得再次出库
- 出库既要支持已组合设备，也要支持 compatible but modification required 的临时配置
- 需要统一任务中心与可用资产调度台

## Confirmed Decisions（已确认决策）

- 保留 whole-machine number 与 component asset numbers 双编号体系
- v1 compatibility 以人工维护 allow-list 为唯一可信来源
- 使用统一任务中心承接 inspection / maintenance / servicing / modification / scrapping
- 允许 management special override，但必须保留 reason / risk acknowledgement / audit trail
- 参数采用 factory / current / project-temporary 三层模型
- freight attribution 在 v1 只做到 project-level，不做 device-level freight allocation
- modification 完成后覆盖 current configuration，但必须保留 original / factory baseline
- 资产台账主要服务公司内部追溯，不受 external audit / tax constraints 驱动

## Non-goals（非目标）

本期明确不做：
- automatic compatibility rules engine
- parameter-derived compatibility inference
- device-level freight allocation
- generic BPM platform
- auto-scheduling / auto-optimization dispatch engine
- external audit compliance ledger redesign
- 所有设备统一升级为顶管机式组合资产模型

## Future Decisions（后续待决事项）

后续阶段再决定：
- 是否引入参数驱动的兼容规则引擎
- 是否对部分非顶管机设备引入轻量 parent-child 关系
- 是否支持多项目拼车运输与分摊
- 是否需要更细颗粒度的寿命维度（如 shell fatigue / console service cycles）
- 是否将运输与外部承运商结算进一步并入财务流程

## Glossary（术语表）

| Term | 定义 |
|---|---|
| whole-machine number | 整机业务编号，用于业务协同、出库配置、项目沟通与调度视图 |
| shell | 机壳，属于可追溯部件资产；可能在项目中留地下报废 |
| core | 机芯，service life、maintenance responsibility 与主要使用寿命锚点 |
| console | 操作台，与核心控制能力相关，可与某些 core 兼容 |
| component asset number | 机壳 / 机芯 / 操作台各自的资产编号，用于 traceability |
| current configuration | 某一 point in time 下实际生效的 shell + core + console 组合关系 |
| time-bounded assembly | 有起止时间的装配关系；用于表达历史装配、拆解、换芯 |
| compatibility | “理论允许组合”的关系，不等于当前已装配 |
| assembly | 已经装配完成并进入当前配置的关系 |
| modification required | 可组合但尚未装配、需先执行改装任务后才能出库 |
| factory baseline | 原厂 / 初始参数，不因项目临时需求被覆盖 |
| current effective parameters | 当前设备运行口径下的有效参数 |
| project-temporary parameters | 某项目临时改装/临时配置下的参数覆盖视图 |
| unified task center | 统一承接 inspection / maintenance / servicing / modification / scrapping 的任务池 |
| special override | 管理层特批放行机制，用于极端紧急情况绕行部分闸门 |
| available now | 当前无需额外改装和阻塞任务即可调度 |
| available after modification | 当前兼容但需要先完成 modification task 才能调度 |

## Baseline Alignment with Existing Repo（与现有系统基线对齐）

本次架构遵循 extend-not-replace 原则，不替换现有基础对象，而是在其上做专项扩展。

| Existing Repo Concept | 当前含义 | 升级后角色 |
|---|---|---|
| `warehouse` | 仓库主数据 | 继续作为物理库存与执行地点主数据 |
| `asset_type` | 资产类型模板 | 继续作为 shell/core/console/其他设备的类型模板载体 |
| `tracked_asset` | 有状态资产实例 | 继续作为 component asset 的基础实例载体 |
| `tracked_asset_document` | 资产文档 | 继续承接文档证据与维保附件 |
| `tracked_asset_event` | 资产事件时间线 | 继续承接 component-level timeline，并扩展事件 taxonomy |
| `stock_order` | 出入库单 | 继续作为出入库主单据，不被替换 |
| `project_equipment_plan` | 项目设备规划 | 继续作为项目侧设备筹备入口，新增组合资产与改装语义 |
| `inventory` | 库存量与库存视角 | 继续保留，作为仓库可视库存的基础能力 |
| `doc/UI设计文档.md` 中的资产/仓库页面 | 页面映射基线 | 后续补充 task center / dispatch board / role visibility 的专项设计 |

升级后新增但不替换的概念包括：
- 组合配置关系（configuration / time-bounded assembly）
- 兼容性 allow-list
- 顶管机专项状态机
- 统一任务中心的资产任务分类
- 调度读模型

## Asset Identity and Numbering Model（资产身份与编号模型）

### 1. 双视图原则

资产身份采用双视图：
- **Business View**：whole-machine number，用于整机视角下的调度、出库、项目沟通
- **Traceability View**：shell number / core number / console number，用于组件级履历、寿命、维保与报废追踪

两者并存，但职责不同。整机视图不是对部件视图的替代。

### 2. current configuration 是运行态真相

系统中的当前运行态以 **current configuration** 为准。

当前配置的核心规则：
- 一个 core 在生命周期内可以关联多个 shell，但这是 time-bounded assembly
- 任一 point in time，只允许存在一个 single current configuration
- whole-machine number 不永久绑定某个 shell
- shell / core / console 的部件履历必须独立保留，不能只沉淀到整机事件里

### 3. 身份口径

建议身份口径如下：
- `whole-machine number`：业务协同编号
- `component asset number`：shell / core / console 的资产编号
- `serial_no`：制造商或物理序列号（如存在）

内部追溯优先于外部审计口径，因此编号体系首先服务于：
- 谁和谁在何时被装配在一起
- 某个 core 曾经在哪些 shell 中使用
- 某个 shell 是否已经地下报废
- 当前哪套配置可以出库

## Compatibility and Configuration Model（兼容性与配置模型）

### 1. compatibility ≠ assembly

系统必须严格区分三个概念：

1. **compatibility**：在业务与技术上允许组合
2. **assembly**：已经实际装配到一起
3. **modification required**：兼容，但当前尚未装配，需要先执行改装任务

因此：
- compatible 不代表 ready to dispatch
- already assembled 才可能在满足闸门时形成 available now
- compatible but not assembled 只能进入 available after modification 或 modification required 视图

### 2. v1 compatibility source of truth

v1 的 compatibility source of truth 为人工维护 allow-list：
- shell ↔ core allow-list
- core ↔ console allow-list

本期不做：
- automatic compatibility rules engine
- parameter-derived compatibility inference

### 3. 出库配置语义

出库配置支持两条主路径：

#### A. 已组合出库（assembled outbound）
- 选择已有 current configuration 的 whole-machine view
- 若无阻塞任务且已满足维护闸门，则可直接发运

#### B. 兼容但需改装出库（compatible-but-needs-modification outbound）
- 选择可兼容的 shell + core + console 组合
- 系统提示 `modification required`
- 创建或挂接对应 modification task
- 改装完成并通过闸门后才可发运

## Parameter Layering Model（参数分层模型）

参数采用三层结构：

### 1. factory baseline
- 表示出厂 / 初始能力与底档参数
- 用于回答“这台设备原本底子是什么”
- 不因项目需求被覆盖

### 2. current effective parameters
- 表示当前 configuration 下真正生效的参数
- modification 完成后，这一层会被更新
- 当前出库、调度、任务判断默认看这一层

### 3. project-temporary parameters
- 表示某项目临时改装或临时适配的参数视图
- 带 project context
- 用于记录项目临时需要，而不是永久覆盖 factory baseline

### 参数覆盖规则

- factory baseline 永远保留
- modification 完成后，current effective parameters 可以被覆盖
- project-temporary parameters 记录项目维度的临时值，不直接抹除 factory baseline

### outer diameter 示例

以 outer diameter 为例：
- factory：设备原始外径规格
- current：当前改装后实际有效外径
- project-temporary：某项目临时要求下的外径配置口径

## Lifecycle State Machines（生命周期状态机）

### 1. 状态机设计原则

状态机必须服务于三件事：
- 判断设备是否可调度
- 判断是否必须进入 inspection / service / modification 路径
- 支持对 buried shell / recovered core 等异常场景进行一致追溯

以下状态在同一对象同一时点必须互斥：
- `available`
- `reserved`
- `in transit`
- `on project`
- `returned quarantine`
- `scrapped`

任何对象只要处于 `on project` 或 `in transit`，都不应被视为 dispatchable。

### 2. shell lifecycle

| State | 含义 | 允许转移 |
|---|---|---|
| `available` | 在库可用，可被装配或预留 | `reserved`, `in transit`, `modification`, `scrapped` |
| `reserved` | 已被出库/改装计划锁定 | `available`, `in transit`, `modification` |
| `in transit` | 发往项目或返库途中 | `on project`, `returned quarantine` |
| `on project` | 在项目现场使用中 | `in transit`, `buried underground`, `modification` |
| `buried underground` | 机壳留在地下，无法正常回收 | `scrapped` |
| `returned quarantine` | 已返库，但尚未完成检查 | `inspection`, `service`, `modification` |
| `inspection` | 检查中 | `available`, `service`, `modification`, `scrapped` |
| `service` | 保养/维修处理中 | `available`, `modification`, `scrapped` |
| `modification` | 改装处理中 | `available`, `service`, `scrapped` |
| `scrapped` | 已报废，终态 | - |

### 3. core lifecycle

| State | 含义 | 允许转移 |
|---|---|---|
| `available` | 在库可用 | `reserved`, `in transit`, `modification`, `service` |
| `reserved` | 已被项目/装配/改装任务锁定 | `available`, `in transit`, `modification` |
| `in transit` | 发往项目或返库途中 | `on project`, `returned quarantine` |
| `on project` | 在项目中承担主要工作寿命消耗 | `in transit`, `modification`, `recovered core` |
| `recovered core` | 从地下遗留机壳中拆回，待返库处置 | `returned quarantine` |
| `returned quarantine` | 已回库，但未完成 inspection | `inspection`, `service`, `modification` |
| `inspection` | 检查中 | `available`, `service`, `modification`, `scrapped` |
| `service` | 保养/维修中 | `available`, `modification`, `scrapped` |
| `modification` | 改装中 | `available`, `service`, `scrapped` |
| `scrapped` | 已报废，终态 | - |

### 4. console lifecycle

| State | 含义 | 允许转移 |
|---|---|---|
| `available` | 在库可用 | `reserved`, `in transit`, `service`, `modification` |
| `reserved` | 被调度/改装锁定 | `available`, `in transit`, `modification` |
| `in transit` | 在途 | `on project`, `returned quarantine` |
| `on project` | 在项目中使用 | `in transit`, `service`, `modification` |
| `returned quarantine` | 回库待检 | `inspection`, `service`, `modification` |
| `inspection` | 检查中 | `available`, `service`, `modification`, `scrapped` |
| `service` | 维修/保养中 | `available`, `modification`, `scrapped` |
| `modification` | 改装中 | `available`, `service`, `scrapped` |
| `scrapped` | 已报废，终态 | - |

### 5. whole-machine business view lifecycle

整机业务视图不是独立物理资产，而是 current configuration 的业务投影，因此其状态受 shell / core / console 和 configuration relation 共同决定。

| State | 含义 | 进入条件 |
|---|---|---|
| `available` | 当前配置完整且满足出库条件 | shell/core/console 都可用，无阻塞任务 |
| `reserved` | 已被计划锁定 | 当前配置已被项目或改单占用 |
| `in transit` | 整机视图正在发运或返库 | configuration relation 已绑定发运单 |
| `on project` | 整机配置在项目现场运行 | current configuration 在现场生效 |
| `returned quarantine` | 整机视图返库待检 | 任一关键部件返库且未完成 inspection |
| `modification` | 整机视图处于改装路径 | configuration 变更尚未完成 |
| `unavailable` | 关键部件缺失或配置不完整 | 例如无兼容 console、shell 已 buried underground |
| `scrapped` | 视图终止 | core 报废或整机业务编号终止使用 |

### 6. configuration relation lifecycle

| State | 含义 | 说明 |
|---|---|---|
| `planned` | 已选定兼容组合，但未开始装配 | 典型场景：compatible but modification required |
| `assembling` | 装配/改装进行中 | 尚未形成 current configuration |
| `active` | 当前有效配置 | single current configuration at a point in time |
| `disassembling` | 拆解中 | 例如换芯、返库拆解、地下回收 |
| `closed` | 历史配置已结束 | 用于时间线回溯 |

### 7. 关键异常场景

#### buried shell / recovered core
- shell 进入 `buried underground`，随后进入 `scrapped`
- core 进入 `recovered core`，返库后必须先进入 `returned quarantine`
- recovered core 未完成 inspection 之前，不能进入 `available`

#### return quarantine is mandatory
- 任何主要设备返库后，不能直接从 `in transit` 跳到 `available`
- 必须先进入 `returned quarantine` → `inspection`
- inspection 结论决定后续进入 `available`、`service`、`modification` 或 `scrapped`

#### mutually exclusive dispatch states
- `available`, `on project`, `in transit` 三者必须互斥
- 只要对象进入 `returned quarantine`, `inspection`, `service`, `modification`，都应退出 `available`

## Unified Task Center（统一任务中心）

### 1. 任务中心的定位

统一任务中心不是 generic BPM platform，而是面向资产运维的统一 work-order 池。它覆盖：
- inspection
- maintenance
- servicing
- modification
- scrapping

其目标是把“是否可出库、是否必须返库隔离、是否需要改装、是否需要报废”统一收敛到一个任务口径下。

### 2. 通用任务字段

所有资产任务至少包含：
- task type
- target asset / target configuration
- trigger source
- owner role
- planned start / planned finish
- blocking flag（是否阻塞出库/调度）
- required evidence
- completion result

### 3. 核心 task taxonomy

| Task Type | 触发场景 | 是否默认阻塞可用性 | 完成条件 |
|---|---|---|---|
| `inspection` | 返库待检、异常返库、埋地机芯回收 | 是 | 检查结论明确，并决定进入 available / maintenance / servicing / modification / scrapping |
| `maintenance` | 设备维护、定期维保 | 是 | 完成维护动作并留下证据 |
| `servicing` | 故障修复、功能恢复 | 是 | 修复完成并通过复核 |
| `modification` | 换芯、改外径、兼容组合装配 | 是 | 新 configuration 生效，相关参数层更新 |
| `scrapping` | 壳体埋地、设备终止使用 | 是 | 报废原因、责任、去向、状态关闭完整 |

### 4. 任务状态

建议任务状态统一为：
- `draft`
- `ready`
- `in progress`
- `waiting review`
- `completed`
- `cancelled`

其中：
- 只要任务处于 `ready` / `in progress` / `waiting review` 且 `blocking flag = true`，相关对象即不可进入 `available`
- `completed` 不是自动可用，仍需根据任务结论和对象状态机更新可用性

### 5. 责任角色

任务中心中的关键责任通常包括：
- 发起人：项目经理、办公室、库房、系统规则
- 执行人：库房、设备负责人、维修人员
- 复核人：办公室或设备负责人
- 特批人：管理层（仅 special override 相关）

### 6. 顶管机与非顶管机的复用边界

统一任务中心支持两层复用：

#### 顶管机 composite task
- 可以绑定 shell / core / console / current configuration
- 可以记录 compatible but modification required 的组合任务
- 可以表达 buried shell / recovered core 等专项场景

#### generic equipment task
- 仍然使用 inspection / maintenance / servicing / modification / scrapping
- 但默认只绑定单一 tracked asset
- 不强制要求 composite-asset fields

因此，generic equipment can use the same task center without composite-asset fields。

## Dispatch / Return / Override Gates（出入库 / 返库 / 特批闸门）

### 1. 标准 outbound flow

标准出库路径为：

1. site PM initiation
2. office review and supplement
3. warehouse execution
4. transport arrangement
5. site receipt

在该流程中，项目经理负责提出需求，办公室负责信息补全和合规审核，库房负责实际执行和装运。

### 2. 标准 return flow

标准返库路径为：

1. project return notice
2. warehouse receipt
3. returned quarantine
4. inspection
5. service / modification（如需要）
6. available

任何主要设备返库后都必须先进入 returned quarantine，不能直接重新出库。

### 3. dispatch gates

设备进入 dispatchable 状态前，至少满足以下 gate：
- required inspection 已完成（如适用）
- required maintenance / servicing 已完成
- 无 blocking task 处于 `ready` / `in progress` / `waiting review`
- current configuration 完整
- 若涉及运输前置审批，则 transport arrangement 所需预算/预付款条件已满足

只要上述条件不满足，就不能从 `available after modification` 或 `reserved` 进入真实发运。

### 4. return quarantine gate

return quarantine 的作用是阻止“返库即出库”。

核心规则：
- 从 `in transit` 返回仓库的主要设备必须先进入 `returned quarantine`
- `returned quarantine` 结束前，不得重新进入 `available`
- inspection 的结论决定进入 `available`、`service`、`modification` 或 `scrapped`

### 5. management special override

special override 仅用于极端紧急场景，且必须由 management approval 触发。

override 最低要求：
- management approval
- reason
- risk acknowledgement
- audit trail
- 被绕过的 gate 列表

special override 不是“直接改状态”，而是一个受控例外流程。即使发生 override，也必须明确：
- 哪些 gate 被绕过
- 谁批准
- 为什么批准
- 批准后是否追加补检、补保养或追认任务

### 6. stock order 与 gate 的关系

`stock_order` 继续作为出入库主单据，但不单独决定是否可放行。实际放行必须同时参考：
- stock order 状态
- unified task center 中的 blocking tasks
- current configuration 是否完整
- return quarantine / inspection 是否关闭
- 是否存在 special override

## Transport Budgeting and Project Freight Attribution（运输预算与项目运费归集）

### 1. transport chain

运输链条在业务上定义为：

1. budget request
2. prepayment
3. transport arrangement
4. shipment execution
5. cost confirmation
6. project allocation

这条链条服务于库房执行，不单独扩展成完整财务结算平台。

### 2. v1 attribution rule

v1 只做 project-level freight attribution：
- 运输费用最终挂到项目
- 不做 device-level freight allocation
- 同一运输单可以包含多个设备，但当前口径仍以项目归集为准

### 3. 与 stock order / project 的绑定关系

运输信息应至少与以下对象建立业务关联：
- outbound / inbound `stock_order`
- project
- 执行仓库
- 承运安排记录

也就是说，transport arrangement 不是脱离出入库流程独立存在，而是跟着项目与库房执行路径走。

### 4. 前置约束

若某次发运要求先完成预算和预付款，则在 transport arrangement 前必须确认：
- budget request 已通过
- prepayment 已落实或已获批豁免
- 发运所对应项目已明确

若上述条件不满足，运输安排不能进入执行状态。

### 5. actor ownership and approval ownership

为保证 project freight attribution chain 可以无人工解释重放，角色分工明确如下：

- **site PM**：提出项目运输需求，确认项目归属与预期到货窗口
- **office**：审核补充运输申请信息，核对项目、单据、预算资料是否齐备；若存在 prepayment exemption，则负责提交豁免流
- **warehouse**：发起具体 budget request、执行 transport arrangement、对接承运方、登记 shipment execution 与回单信息
- **management**：审批预算超限、prepayment exemption 等高风险运输例外事项
- **cost confirmation owner**：默认由 warehouse 录入运费实际值，office 负责复核归属项目与单据一致性

### 6. transport-related task mapping

运输链路与任务中心的映射规则如下：
- `budget request`：可挂为运输准备任务，不直接改变资产状态
- `prepayment pending`：若未完成则阻塞 transport arrangement
- `transport arrangement`：完成后允许对象从 `reserved` 进入真实发运路径
- `cost confirmation`：不影响返库可用性，但影响项目成本闭环
- `project allocation`：必须在 cost confirmation 后关闭，才视为运输链路完成

### 7. 明确排除项

本期明确不做：
- device-level freight allocation
- 对单台设备的精细成本摊销
- 承运商结算平台化

## History / Query Model and Event Taxonomy（履历查询模型与事件分类）

### 1. 设计目标

履历模型必须支持：
- query by shell
- query by core
- query by whole-machine number
- point-in-time reconstruction

历史不能只依赖整机视图；component-level history 必须独立存在。

### 2. event taxonomy

建议至少覆盖以下事件类型：

1. `asset_created`
2. `assembly_started`
3. `assembly_completed`
4. `disassembly_started`
5. `disassembly_completed`
6. `core_swapped`
7. `modification_completed`
8. `inspection_completed`
9. `maintenance_completed`
10. `service_completed`
11. `dispatch_completed`
12. `return_received`
13. `shell_buried_underground`
14. `shell_scrapped`
15. `core_recovered`
16. `special_override_approved`
17. `transport_arranged`
18. `transport_cost_confirmed`

### 3. query by shell

query by shell 应至少返回：
- shell 当前状态
- shell 曾配过哪些 core
- shell 曾参与过哪些 whole-machine view
- shell 是否 buried underground / scrapped
- 与 shell 相关的 inspection / maintenance / modification / dispatch / return 事件

### 4. query by core

query by core 应至少返回：
- core 当前状态
- core 的 service life 相关履历
- core 曾进入过哪些 shell
- core 是否发生过 recovered core 场景
- 与 core 相关的 maintenance / servicing / modification / dispatch / return 事件

### 5. whole-machine history

whole-machine view 的历史不是单独替代 component history，而是通过 current configuration / time-bounded assembly 反推出：
- 某个业务编号在某段时间由哪些 shell / core / console 构成
- 当时处于哪个项目
- 是否通过 special override 发运

### 6. buried-shell / recovered-core case

对 buried shell / recovered core 场景，历史必须能回答：
- 哪个项目导致 shell buried underground
- shell 何时报废
- 被回收的是哪个 core
- recovered core 后续进入了哪些 inspection / service / modification 路径

## Dispatch-board Read Model and Availability Formula（调度台读模型与可用性公式）

### 1. dispatch-board 目标

调度台是 read model，不是 auto-scheduling engine。它的职责是把资产可用性、改装需求、阻塞原因、在途状态和项目占用统一投影出来，供调度决策使用。

### 2. 最小状态标签

调度台至少显示以下状态标签：
- `available now`
- `available after modification`
- `blocked by maintenance`
- `reserved`
- `in transit`
- `on project`
- `scrapped`

必要时可补充：
- `returned quarantine`
- `configuration incomplete`

### 3. availability formula

是否可调度，不由单一字段决定，而由以下因素共同计算：

`availability = state + blocking work + configuration completeness + compatibility + reservation + transit + override`

其中：
- `state`：对象当前生命周期状态
- `blocking work`：是否存在 inspection / maintenance / servicing / modification 等阻塞任务
- `configuration completeness`：whole-machine current configuration 是否完整
- `compatibility`：若不是已装配配置，是否至少满足 allow-list
- `reservation`：是否已被其他项目或改单锁定
- `transit`：是否已在途
- `override`：是否存在合法 special override

### 4. available now

满足以下条件时进入 `available now`：
- 当前状态为 `available`
- 无 blocking work
- current configuration 已完成
- 不在 `reserved` / `in transit` / `on project` / `returned quarantine`

### 5. available after modification

满足以下条件时进入 `available after modification`：
- 组件之间 compatible
- 当前尚未形成可发运 configuration，或 modification 任务尚未完成
- 不存在不可恢复报废状态

换言之，`available after modification` 不是立即可发运，而是“具备改装后可用的潜力”。

### 6. blocked by maintenance

当存在以下任一情况时，应显示 `blocked by maintenance`：
- 有 blocking inspection 任务未关闭
- 有 blocking maintenance / servicing 任务未关闭
- 返库后仍在 returned quarantine

### 7. override 在调度台中的呈现

若某对象依赖 special override 才能放行，调度台不应直接把它显示成普通 `available now`，而应明确标记：
- 该对象有被绕过的 gate
- override 的有效期/审批状态
- 是否还需补检或补任务

## Non-TBM Modification Boundary（非顶管机改装边界）

### 1. 顶管机是 composite-asset special case

顶管机之所以需要组合资产建模，是因为它天然存在：
- shell / core / console 的独立身份
- component compatibility
- time-bounded assembly
- 核心寿命跟 core 走而不是跟整机视图走

这不是所有设备的共性。

### 2. generic equipment task / event model

对于其他可改装设备，默认使用：
- single-asset tracked asset
- unified task center
- 通用 modification / maintenance / servicing / scrapping 事件
- 可选的参数变更记录

即：non-TBM 设备默认走 single-asset + task/event + optional parameter change，不默认进入 shell/core/console 式组合模型。

### 3. 未来扩展缝

若未来某些设备需要轻量 parent-child 结构，可在后续阶段单独扩展，但本期不把所有设备都升级为 composite-asset model。

## Bounded Contexts / Aggregates / Schema Delta（边界上下文 / 聚合 / 增量扩展提案）

### 1. capability zones / bounded contexts

建议最少拆分以下能力区：
- asset master data
- compatibility / configuration
- unified task center
- dispatch execution
- transport attribution
- approval
- dispatch-board read model

### 2. aggregate focus

关键聚合建议包括：
- component asset（shell / core / console）
- whole-machine business view
- configuration relation
- work order
- stock order
- transport arrangement

### 3. additive schema delta only

schema delta 原则：
- incremental
- non-destructive
- do not replace tracked_asset / stock_order / tracked_asset_event

新增对象应尽量围绕以下能力增加：
- configuration relation
- compatibility allow-list
- unified task/work order
- transport attribution record
- dispatch-board projection
